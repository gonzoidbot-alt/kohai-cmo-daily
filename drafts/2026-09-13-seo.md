## Fix #1 (Severity: HIGH) — robots.txt blocks every AI crawler Kohai's GEO strategy depends on

**The problem.** kohai.co/robots.txt is managed by Cloudflare ("BEGIN Cloudflare Managed content" block, `Content-Signal: search=yes,ai-train=no,use=reference`) and explicitly disallows these user-agents site-wide:

- GPTBot (OpenAI / ChatGPT)
- ClaudeBot (Anthropic / Claude)
- Google-Extended (Gemini grounding)
- CCBot (Common Crawl — a major upstream source for many AI training sets)
- Bytespider (ByteDance), Amazonbot (Alexa), Applebot-Extended (Apple Intelligence), meta-externalagent (Meta AI), CloudflareBrowserRenderingCrawler

This directly contradicts the strategy: 04-content-strategy.md sets GEO as a daily channel and lists "ensure ChatGPT/Perplexity describe Kohai as 'AI colleagues/workforce platform with approval gates and open-weight models'" as a week-1 must-fix, and 06-gtm-funnel-playbook.md cites G2's finding that 51% of B2B buyers now start research with an AI chatbot. The AI engines cannot describe — let alone cite — a site their crawlers are forbidden to fetch. Every AI-visibility audit in the GTM plan will run against this headwind.

Note the nuance in the Cloudflare block: `ai-train=no` (denied) but **`ai-input` has no signal set** — meaning real-time retrieval/RAG for AI answers is neither granted nor restricted via signals. The per-bot `Disallow: /` lines are what actually block fetching. Kohai's positioning is "open-weight, private by default" — blocking *training* crawlers while *allowing* answer-grounding crawlers is consistent with the brand. The current file blocks both, which is the worst of both worlds for the stated strategy.

**Recommended robots.txt** (paste in place of the Cloudflare managed block — keep the `ai-train` restriction, lift the fetch blocks for grounding crawlers):

```
# BEGIN Kohai managed robots.txt (replaces Cloudflare managed AI-crawler block)

User-agent: *
Content-Signal: search=yes,ai-train=no,use=reference
Allow: /

# Allow AI answer engines to fetch and cite us (GEO strategy, 04-content-strategy.md)
User-agent: GPTBot
Allow: /

User-agent: OAI-SearchBot
Allow: /

User-agent: ChatGPT-User
Allow: /

User-agent: ClaudeBot
Allow: /

User-agent: Claude-User
Allow: /

User-agent: Claude-SearchBot
Allow: /

User-agent: Google-Extended
Allow: /

User-agent: PerplexityBot
Allow: /

User-agent: Perplexity-User
Allow: /

User-agent: Applebot
Allow: /

User-agent: meta-externalagent
Allow: /

# Keep training-crawler blocks where the brand story supports it
User-agent: CCBot
Disallow: /

User-agent: Bytespider
Disallow: /

User-agent: Amazonbot
Disallow: /

User-agent: Applebot-Extended
Disallow: /

# END Kohai managed robots.txt

User-agent: *
Allow: /

Sitemap: https://kohai.co/sitemap-index.xml
```

**Mechanics for Gabe:** the Disallow block is Cloudflare-managed. It is toggled in Cloudflare Dashboard → the domain → (AI Crawl Control / Security → Bots) — either flip the per-bot toggles there, or disable the managed robots.txt injection and serve the file above. Verify after the change with `curl -s https://kohai.co/robots.txt | grep -A1 GPTBot`. Cloudflare may take a few minutes to reflect the change.

**Caveat (flagged, not verified):** allowing these bots is a rights grant. If Gabe wants maximum conservatism, the minimal move is to allow only OAI-SearchBot, ChatGPT-User, PerplexityBot, and ClaudeBot (the answer/retrieval bots) and keep everything else disallowed. Either way, the current blanket block is the single highest-severity SEO/GEO issue on the site.

## Keyword-gap observation — no pages target the "X alternative" intent; /vs/* pages match a different query

**What 04 calls money queries:** "AI employees for small business", "AI workforce platform", "hire AI employees", "Lindy alternative", "Artisan alternative" (plus long-tail "AI chief of staff").

**What exists (sitemap-0.xml, 50 URLs, verified today):** 11 /vs/* pages (lindy, artisan, sintra, marblism, relevance-ai, 11x, claude, hermes, openclaw, viktor, virtual-assistant) plus 9 industry/solution pages. All of these are built for "X vs Y" intent — a direct-comparison query, usually searched by someone already weighing both products.

**The gap:** "Lindy alternative" and "Artisan alternative" are a *different* query with different SERP competition and a different searcher (someone shopping for replacements, not comparing two named options). Today's SERP checks (2 web searches, 2026-09-13):
- "Lindy alternative" — top organic results are third-party alternatives pages (e.g. chatbotkit.com/alternatives/lindy) and Lindy's own properties; **no kohai.co URL ranked in the results returned**. Kohai's /vs/lindy page is built for the "vs" query, not this one.
- "hire AI employees" — top results are Sintra's homepage ("Hire Your First AI Employees") and third-party guides (sistava.com, kuse.ai, Reddit, LinkedIn Pulse); **no kohai.co URL ranked**, despite Kohai's blog having "what-is-an-ai-employee" and related posts. Sintra's exact-match homepage H1 is winning the query Kohai's pricing page should compete for.

**Recommendation (one move, two intents):** ship one "alternatives" page per priority competitor — /alternatives/lindy-alternative, /alternatives/artisan-alternative — structured for the replacement-intent query (H1: "The best Lindy alternative in 2026", H2s: why teams switch, pricing comparison, migration notes), internally linking to the existing /vs/lindy page rather than replacing it. This is also the cheapest citation surface for AI engines: "alternative" pages are the single most-quoted page type in AI shopping answers. Marked **unverified**: I did not run rank-tracking on these queries; the "no kohai.co ranked" observation reflects only the top ~5 web-search results returned per query today.

Secondary gap, same root cause: "AI chief of staff" (04 long-tail list) has no exact-match page; Mochi is the product's Chief of Staff and the homepage never surfaces that term in a title or H2 (homepage `<title>` verified today: "Kōhai — Onboard AI colleagues. Get work finished.").
