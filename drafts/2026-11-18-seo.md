## Fix 1 — HIGH: 46 /lp/* ad landers are in the sitemap and indexable, with zero internal links pointing at them

**The problem.** Sitemap-0.xml now holds **124 URLs; 46 of them are /lp/* pages** (law-firms 14, compounding 6, logistics 5, saas 4, private-ai 3, accounting 2, cost 2, sales-bd 2, team 2, agencies 1, construction 1, finance 1, hr 1, local-services 1, solo-founders 1). I checked all of the site's highest-authority pages for inbound links to any of them — homepage, /blog, /blog/ai-for-small-business, /pricing, /guides, /solutions/smb, /solutions/solopreneurs, /professional-services, /saas-and-product-led, /technology, /vs/lindy — **every single one links to 0 /lp/ pages.** The fleet is reachable only via the sitemap and paid-ads entry URLs.

That means the fleet sits in the worst possible position: it is *in* the organic index (no noindex, self-canonical, sitemap-listed), so Google will crawl and index it — but with no internal PageRank, ad-headline titles that match zero search demand ("The brief starts itself | Kōhai", "Someone on your team just pasted the client list into a chatbot"), and 14 near-identical templates for one vertical, it can only drag quality signals down (doorway-page classification risk) and burn crawl budget. None of these pages can rank for anything as shipped; they can only dilute. Body depth is fine (~711 words on the law-firms sample), so the pages themselves aren't thin — the linkage and title strategy is.

**The fix is a decision, not a rewrite — two paths, pick per vertical:**

**Path A — pure paid-ads landers (recommended for compounding, cost, private-ai, saas, team: 17 pages):** keep them out of the organic index entirely.

```html
<!-- add to <head> of every /lp/* page -->
<meta name="robots" content="noindex, follow">
```
and drop them from the sitemap (Astro sitemap filter, `astro.config.mjs`):
```js
sitemap: [{ filter: (page) => !page.includes('/lp/') }]
```

**Path B — strategic verticals with existing guide clusters (law-firms first: 14 pages + 4 legal /guides):** link them in from the matching organic pages so they inherit authority, then the vertical can actually rank. Add to /guides/lawyers (and the other three legal guides):

```html
<!-- Related walkthroughs (before footer CTA) -->
<section>
  <h2>See Kōhai running in a firm like yours</h2>
  <ul>
    <li><a href="/lp/law-firms/the-brief-starts-itself">Answering a motion: first draft before you start</a></li>
    <li><a href="/lp/law-firms/deposition-outline-by-morning">Deposition outline ready by morning</a></li>
    <li><a href="/lp/law-firms/discovery-documents-summarized-overnight">Discovery summarized overnight</a></li>
    <li><a href="/lp/law-firms/conflicts-checked-before-you-say-yes">Conflict checks before you say yes</a></li>
  </ul>
</section>
```

Path B pages should also get one keyword-bearing H2 in the body (current H1s are ad copy — that's fine — but a question-style H2 gives the crawler something to rank, e.g. "How do law firms use AI teammates?").

**Rollout note:** if Path A/B can't be decided quickly, at minimum pull all 46 from the sitemap now — sitemap removal is zero-risk and stops the crawl-budget burn while the decision is pending.

## Fix 2 — MEDIUM-HIGH: all 21 blog posts ship zero Article structured data

**The problem.** Verified on /blog/what-is-an-ai-employee (the site's best organic-reach asset): the page carries only sitewide Organization + WebSite + ImageObject JSON-LD — **no `BlogPosting`/`Article` block anywhere**. The blog is the only part of the site with genuine keyword-bearing titles ("AI for small business", "What is an AI teammate?", "The best AI tools for business") and therefore the pages most likely to rank organically and get quoted by AI engines. Article schema is the cheapest authority signal there: it gives Google and GEO engines author, date, and publisher relationships that the visible DOM renders inconsistently, and eligibility for enhanced search presentation.

**Copy-paste snippet** (template it in the blog layout so it applies to all 21 posts; values below from the live page):

```json
{
  "@context": "https://schema.org",
  "@type": "BlogPosting",
  "headline": "What is an AI teammate?",
  "url": "https://kohai.co/blog/what-is-an-ai-employee",
  "image": "https://kohai.co/images/og/default.jpg",
  "datePublished": "2026-09-09",
  "dateModified": "2026-09-09",
  "author": { "@type": "Organization", "name": "Kōhai" },
  "publisher": {
    "@type": "Organization",
    "name": "Kōhai",
    "logo": { "@type": "ImageObject", "url": "https://kohai.co/images/brand/mark.svg" }
  }
}
```

**Rollout note:** one edit in the blog post layout component — pull `Astro.props.title/url/image/dates` into the JSON block. Confirm `datePublished` exists per post in the content collection frontmatter; if it doesn't, add it (dates are also a ranking-freshness signal). This complements, not duplicates, yesterday's FAQPage fix for /vs/* and last week's Product/Offer fix for /pricing — same program, one page-type at a time.
